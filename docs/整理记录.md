# 博客整理全过程记录

> 记录从「Hexo 换成 Fuwari」到「笔记自动同步、图片本地化、多级 URL、双链、Cloudflare 部署」的完整过程，以及每一步为什么这么做。

---

## 1. 起点：Hexo → Fuwari（Astro）

**做了什么**：删掉 `d:\HEXO` 里的 Hexo 工程，换成 Fuwari（Astro + Svelte + Tailwind）模板。

**为什么**：Hexo 的 landscape 主题功能老旧，Fuwari 自带暗色模式、Pagefind 搜索、目录、RSS、分类/标签体系，且是静态输出，部署成本低。

**踩到的坑**：上游 Fuwari 的 `ImageWrapper.astro` 用 `import.meta.glob("../../**")` 把整个项目（含 CSS）当副作用导入，导致 `markdown.css` 里的 `@apply link` 偶发找不到类。修复方式：新建 `src/styles/index.ts` 显式按顺序导入样式，并把 glob 收窄到图片扩展名。

---

## 2. 笔记同步：读原库，写副本

**做了什么**：`scripts/sync-notes.mjs` 扫描 `D:\ObsidianFirstNotes`，在内存里转换格式，写到 `src/content/posts/notes/`。

**为什么这么做（而不是直接把笔记搬进博客）**：
- Obsidian 的 frontmatter 是 `created`，博客要 `published`，字段不兼容
- 直接搬会让源库和博客强耦合，改一处两边都受影响
- 部署到 Vercel/Cloudflare 时源库根本不存在，只有生成好的副本能提交

**关键设计**：源库**只读**（`readFileSync` / `statSync`），任何转换都只发生在副本上。这是后续所有整理操作的前提。

---

## 3. 发布范围：三次调整

| 阶段 | 策略 | 结果 | 为什么改 |
|---|---|---|---|
| 第一次 | 全量 102 篇 | 太乱、图片全裂 | 一开始只想「都放上去」 |
| 第二次 | 只发精选 5 篇 | 用户觉得内容太少 | 修正过度 |
| 第三次（最终） | 排除剪藏/日记后全量 88 篇 | 结构清晰 | 内容要全，但靠 URL/分类解决乱 |

**为什么剪藏默认不发**：`Embedded/Clippings` 是 B 站视频转写 + 公众号文章，正文极长、外链图几百张，混进目录会破坏可读性。需要时在笔记里加 `publish: true` 单独放行。

---

## 4. 图片：从「全裂」到「全部本地化」

**问题一：CSDN 防盗链**
CSDN 图床对 `Referer` 为博客域名的请求返回 403，对无 Referer 请求返回 200。
**解决**：同步时用无 Referer 的请求下载图片，按 `content-type` 判断真实格式存到本地。

**问题二：裸文件名歧义**
Obsidian 里写 `![[a.png]]`，全库有多个 `a.png`（PCB、Clippings、操作系统各一份）。旧逻辑「全库同名第一个」会抓错图。
**解决**：解析顺序改为
1. 笔记所在目录
2. 逐级父目录的 `assets/`、`asserts/`、`asserts/Photo/`、`*.assets/`
3. 全库唯一同名
4. 都没有就丢弃（不留破图）

**问题三：超限图片**
动图/超大图触发 sharp 的像素上限。
**解决**：`width*height*帧数 > 1e8` 时自动缩到 4096 内，动图只保留首帧。

**问题四：大小写**
Windows 上 `22.PNG` 与 `22.png` 是同一个文件，提交到 Linux CI 就找不到。
**解决**：扩展名统一小写，按大小写不敏感去重。

## 5. 分类体系：反复试错后的最终方案

| 尝试 | 结果 | 问题 |
|---|---|---|
| 按顶层目录（嵌入式/学习笔记） | 99 篇挤在一个分类 | 太粗 |
| 按整棵目录树 | 出现 `嵌入式/硬件电路/扩展资料/基础知识点/进阶` | 太细 |
| 两级（父/子） | 出现 `硬件电路/扩展资料` 计数被拆 | 用户觉得乱 |
| **最终：具体主题平铺** | 7 个一级分类 | 清晰 |

**为什么最后选平铺**：分类是给读者导航用的，不是复刻文件系统。`FreeRTOS`、`计算机操作系统`、`硬件电路`、`知识点`、`效率工具`、`PID 控制`、`OTA-BootLoader` 这 7 个已经能覆盖全部内容，再加层级只会增加点击成本。

**细分需求改用标签**：笔记里的 `tags` 天然支持多维度，不需要动分类结构。

## 6. 排序：首页按章节，归档按日期

- 首页/上下篇：按 `order`（源库目录顺序 + 自然排序），保证 `01 → 02 → 03` 连贯
- 归档页：按 `published` 倒序，最新在前
- 总目录：按「标题里的章节号」排序（`1.1.1 < 1.1.2 < 2.1`），而不是文件系统顺序

**为什么要分开**：教程式阅读需要固定顺序，但"最近更新了什么"需要时间顺序。同一份数据服务两种诉求，只能在不同页面用不同排序。

---

## 7. URL 与双链

**URL 多级**：`/posts/notes/freeRTOS/01_freertos入门/`，由源库目录结构生成。
**为什么**：扁平 URL 无法看出文章归属，多级路径对搜索引擎和分享更友好。

**双链**：`[[笔记名]]`、`[[笔记名|别名]]` 转成站内相对链接。
**为什么用相对链接**：站点有两个部署路径（`/HexoNotes/` 和 `/`），绝对路径会有一边 404；相对链接两边都能用。
**找不到目标时**降级为纯文本，避免死链。

## 8. 部署：三次迁移

1. **GitHub Pages**（`520luxun.github.io/HexoNotes/`）
   - 用 `gh-pages` 分支发布（Pages API 无法由 Actions 自动启用）
2. **Gitee Pages** —— 失败
   - 仓库正常，但 `/pages` 设置页 404，Gitee 已停止免费 Pages 新开通
3. **Cloudflare Pages**（`hexonotes.pages.dev`）—— 最终主站
   - 免服务器、免备案、连 Git 自动构建
   - 环境变量 `DEPLOY_SITE` / `DEPLOY_BASE=/` 切换根路径构建

**为什么放弃自定义域名 `blog.luxunacc.xyz`**：Cloudflare Pages 绑域名要求把 NS 迁到 Cloudflare，而 `api.luxunacc.xyz` 承载比赛项目的 API 与视频，迁移有中断风险，不值得。

---

## 9. 质量保障

- **`pnpm audit:site`**：扫描构建产物里所有图片、样式、脚本、站内链接、页面，逐个请求验证状态码（903 个 URL）
- **CI 失败日志上报**：GitHub Actions 失败时把日志尾部推到 `ci-logs` 分支 / 提交状态，因为未登录看不到 Actions 日志
- **构建封装**：`scripts/build.mjs` 统一处理同步 + 构建 + Pagefind，并放宽工具环境的批量删除阈值

---

## 10. 现在的日常操作

```bash
# 写笔记 → 发布 → 双平台自动重建
pnpm push:all

# 只看会同步哪些笔记
pnpm sync-notes:preview

# 本地预览
pnpm dev

# 全站体检
pnpm audit:site
```

## 11. 维护注意

- `src/content/posts/notes/` 是**生成目录**，手改会被下次同步覆盖
- 源库 `D:\ObsidianFirstNotes` 永远不要被脚本写入，转换只发生在副本
- 分类来自源库第二层目录名（经 `notes-sync.config.json` 的 `categoryMap` 映射），改名只改映射表
- 想发剪藏：在该笔记 frontmatter 加 `publish: true`
